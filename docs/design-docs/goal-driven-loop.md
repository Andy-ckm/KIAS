# AgentGuard 借鉴 Claude Code /goal 和 Ralph Loop

> 参考来源：Claude Code /goal 命令、Ralph Loop 设计模式
> 关键词：目标驱动、裁判分离、双模型评估

## 核心设计

### 1. Ralph Loop - 目标驱动循环

> 给 Agent 设定一个目标，让它自己不断迭代，失败了就重来，直到目标达成。

**特点**：
- 设定目标就开跑
- 每轮结束后自动判断是否达成
- 未达成继续下一轮，达成自动停止
- 跨会话保持目标

### 2. /goal 命令

```bash
# 设定目标
/goal test/auth 下所有测试通过，lint 干净

# 查看状态
/goal

# 清除目标
/goal clear
```

**运行状态面板**：
- 已运行时间
- 轮次数
- Token 消耗

### 3. 裁判分离（最关键的设计差异）

**Codex 做法**：工作模型自己做「完成审计」
- 干活的人，同时也是验收的人
- 容易把「产出东西」等同于「达成目标」

**Claude Code 做法**：裁判分离
- 干活的归干活，验收的归验收
- 独立小模型（Haiku）判断是否满足条件
- 未满足返回理由，作为下一轮方向指引

### 4. 双模型评估

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   ┌──────────────┐    ┌──────────────┐    ┌──────────────┐  │
│   │   Worker     │───▶│  评估模型    │───▶│   决策       │  │
│   │  (主模型)    │    │  (Haiku)     │    │  继续/停止   │  │
│   └──────────────┘    └──────────────┘    └──────────────┘  │
│          │                   │                   │          │
│          │                   ▼                   │          │
│          │           ┌──────────────┐            │          │
│          │           │   理由反馈   │            │          │
│          │           └──────────────┘            │          │
│          │                   │                   │          │
│          └───────────────────┴───────────────────┘          │
│                       下一轮方向指引                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**为什么这么设计**：
- 让一个模型自己判断「我做完了没」，容易把「产出东西」等同于「达成目标」
- 独立模型评估，多一层制衡
- 不能让模型既当运动员，又当裁判

### 5. 好目标三要素

| 要素 | 描述 | 示例 |
|------|------|------|
| **可衡量的终态** | 测试结果、构建退出码、文件数量 | `npm test 退出码为 0` |
| **验证方式** | 怎么证明完成了 | `git status 干净` |
| **不能破坏的约束** | 过程中不能动什么 | `不修改其他测试文件` |

**条件限制**：
- 最长 4000 字符
- 可以写运行时长限制：「20 轮后如果没完成就停下来」
- 评估模型只能看对话内容，不能独立运行命令

### 6. 三种持续工作方式

| 方式 | 下一轮何时开始 | 何时停止 |
|------|----------------|----------|
| `/goal` | 上一轮结束后 | 独立模型确认条件达成 |
| `/loop` | 定时间隔触发 | 你手动停，或 Claude 觉得做完了 |
| `Stop hook` | 上一轮结束后 | 你自己的脚本或 prompt 决定 |

## 创新点

### 1. 裁判分离 + 对抗机制

结合 MiniMax 的 Worker-Verifier 对抗机制：
- Worker 执行任务
- Verifier 验证结果
- 评估模型判断是否达成目标
- 三重制衡，确保质量

### 2. 目标驱动 + 状态机

结合确定性状态机：
- 目标设定 → 状态机启动
- 每轮执行 → 状态更新
- 评估判断 → 状态转移
- 目标达成 → 状态机停止

### 3. 轻量评估模型

使用轻量模型（如 Haiku）做评估：
- Token 成本基本可以忽略
- 独立视角，不受主模型影响
- 快速判断，不阻塞主流程
