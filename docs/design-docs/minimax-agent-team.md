# KIAS 借鉴 MiniMax Agent Team 设计

> 参考来源：MiniMax Agent Team 官方技术博客
> 链接：https://mp.weixin.qq.com/s/TIL7o92f71DsPPLWT4_37A

## 核心洞察

### 单 Agent 四大痛点

| 痛点 | 描述 | KIAS 解决方案 |
|------|------|--------------|
| **中途停摆** | 上下文焦虑，做 3 件就停 | Engine 驱动，确定性状态机 |
| **越跑越笨** | 偏差累积，无法自检 | Worker-Verifier 对抗机制 |
| **无法响应** | IM 场景用户等待过久 | Owner 秒回 + Worker 后台执行 |
| **角色混乱** | 单 Agent 无法真正分工 | Owner-Worker-Verifier 三角色架构 |

### 核心认知

> **多 Agent 系统不是 prompt 编排，而是一套需要持续运行和维护的基础设施。**

Prompt 只是其中很薄的一层，真正的核心是 Harness（引擎）：
- 任务管理
- 状态恢复
- 权限控制
- 过程追溯

## 架构设计：Owner-Worker-Verifier

### 三角色定义

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   ┌──────────────┐    ┌──────────────┐    ┌──────────────┐  │
│   │    Owner     │───▶│    Worker    │───▶│   Verifier   │  │
│   │  (项目经理)  │    │  (执行者)    │    │  (质量门禁)  │  │
│   └──────────────┘    └──────────────┘    └──────────────┘  │
│          │                   ▲                   │          │
│          │                   └───────────────────┘          │
│          │              对抗式迭代循环                      │
│          ▼                                                  │
│   ┌──────────────┐                                          │
│   │   Engine     │                                          │
│   │ (确定性引擎) │                                          │
│   └──────────────┘                                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### Owner（控制面）
- 理解用户目标
- 拆分子任务
- 决定执行顺序
- 分配 Worker
- 合并结果
- 控制停止条件

### Worker（执行面）
- 具体执行任务
- 不同 Worker 有不同工具、上下文、输出要求
- 专业化角色：检索、写代码、生成文档、处理表格

### Verifier（质量门禁）
- 检查事实来源
- 跑代码测试
- 核对格式要求
- 对 Worker 结果提出修改意见

### 关键设计：对抗关系

> Worker 停止的条件是 Verifier 启动的原因，
> Verifier 停止的条件是尽可能发现 Worker 的问题，
> 发现的问题又成为 Worker 重新启动的原因。

## 核心创新点

### 1. 对抗性质量门禁

Worker 和 Verifier 之间是**对抗关系**，类似企业里研发和质量部门：

```rust
// Worker 想"完事退出"
// Verifier 想"挑出问题让 Worker 重做"
// 双方都以"运行结束"为目标
// 一方结束触发另一方启动
```

### 2. 确定性代码逻辑驱动

用**可靠的状态机**管理 Agent 运行周期，而不是依赖模型的自由判断：

- 什么时候该验证 → 引擎层面硬性约束
- 什么时候该重试 → 引擎层面硬性约束
- 什么时候该停止 → 引擎层面硬性约束

### 3. 上下文隔离

每个 task 一个独立 session，Context 隔离：
- 不污染其他 task
- 节省宝贵的上下文窗口
- 借鉴 Harness/Ralph-Loop 思想

### 4. Agent 间通讯

Agent 与人类同权，共用一组动词：
- 用户能做的，Agent 也能做
- Engine 也能做
- 三种调用方平权，共享同一组接口

## 四大落地场景

### 1. IM 场景

**痛点**：用户发消息期待秒回，但任务需要几分钟

**解决方案**：
- 主 Agent 秒回：收到，目标确认，我会怎么做
- 具体任务拆到后台，分配给不同 Worker 并行执行
- 关键节点汇报：任务开始、遇到卡点、需要决定、已完成

**体验**：像一个能秒回你微信、同时后台还在帮你干活的同事

### 2. Coding 场景

**角色分工**：
- Owner：判断任务是否值得启动 Team
- Developer：负责实现，输出 diff、修改理由、潜在风险
- Tester：负责找现有测试入口来验证结果
- Reviewer：检查抽象边界、兼容性、错误处理、依赖引入

### 3. 研究场景

**痛点**：速度慢、视角单一、证据链管理难、上下文易被污染

**解决方案**：
- 把研究过程拆成多条并行的信息通道
- 不同 Worker 从不同角度搜集信息
- Verifier 确保结论站得住脚：来源可复查、信息不过时

### 4. 办公文档场景

**痛点**：太多信息挤在同一个上下文和执行循环里

**解决方案**：
- Planner：定义文档目标和结构
- Writer：负责正文
- Formatter：负责版式和文件对象
- Tool Agent：调用具体的文档工具
- Evaluator：独立检查内容、格式和文件完整性

## 成本控制

### 三类成本

| 成本类型 | 描述 | KIAS 控制策略 |
|----------|------|--------------|
| **交接成本** | Agent 间信息传递 | 结构化文件和摘要通信 |
| **共享成本** | 所有 Agent 看到所有信息 | 按需加载，只看相关摘要 |
| **聚合成本** | 合并多份结果 | Owner 真实精力合并 |

### Verifier 成本平衡

1. **验证本身消耗**：认真验证要花时间和 token
2. **重试成本**：Worker 改、被退回、再改、再退回
3. **人类决策成本**：高风险动作需要人类签字

---

## 决策判断

> Team 不是默认选项，是策略选项。

- 任务越复杂、链路越长、风险越高、经验越可复用 → 值得上 Team
- 任务越短、越低风险、越确定 → 单 Agent 甚至脚本就够了
