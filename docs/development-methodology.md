# KIAS 开发方法论 — 顶层执行原则

> 钱学森："系统工程是组织管理的技术。"
> 核心：先评估，再开发。不评估不动手。

## 一、铁律：四步开发法

```
┌─────────────────────────────────────────────────────┐
│  Step 1: 评估      Step 2: 审视                      │
│  ─────────────    ─────────────                      │
│  这个功能           现有系统                          │
│  真的需要吗？       能覆盖吗？                        │
│       │                  │                           │
│       ▼                  ▼                           │
│  Step 3: 方案      Step 4: 开发                      │
│  ─────────────    ─────────────                      │
│  怎么做？           按方案执行                        │
│  做到什么程度？     不超范围                          │
└─────────────────────────────────────────────────────┘

违反铁律 = 返工。不接受"先堆上去再说"。
```

## 二、评估清单（Step 1 + Step 2）

每个新功能必须回答以下问题：

```markdown
## 功能评估表

### 1. 必要性
- 解决什么问题？（具体场景）
- 不做会怎样？（影响程度：致命/严重/一般/无影响）

### 2. 重复性
- 现有功能能否覆盖？（列出相关模块）
- 能否扩展现有模块？（而非新建）

### 3. 工程化
- 参考来源？（论文/开源项目，必须下载分析）
- 测试策略？（不是 assert(true)）

### 4. 整体影响
- 架构分层影响？（L0/L1/L2/L3）
- 编译时间影响？
- 其他 crate 影响？
```

## 三、架构审视（Step 2 补充）

定期审视（每个 Sprint 开始前）：

```
1. 模块清单：列出所有 crate 和核心模块
2. 功能映射：每个模块解决什么问题
3. 依赖检查：是否有跨层依赖
4. 重复检测：是否有功能重叠
5. 缺失分析：是否有需求未覆盖
```

## 四、方案制定（Step 3）

```markdown
## 开发方案模板

### 功能名称
### 目标
### 范围（明确不做什么）
### 实现方式
### 测试策略
### 文档计划
### 验收标准
```

## 五、执行规范（Step 4）

1. **不超范围**：方案写什么做什么，不临时加功能
2. **质量门禁**：fmt + clippy + test，零容忍
3. **文档同步**：代码变更必须同步文档
4. **提交规范**：`type(scope): description`

## 六、集成方式

本方法论通过以下方式集成到 KIAS 开发：

1. **docs/development-methodology.md**：本文档，顶层方法论
2. **docs/feature-evaluation-checklist.md**：评估清单，可直接填写
3. **PR 模板**：必须包含评估表
4. **Sprint 回顾**：检查是否遵守四步法
