> 经验来源：2026-05-16 ~ 2026-05-23 多个开发session

## 一、Rust 编译类陷阱

### 1.1 E0592 — 重复的 lifetime 参数 ⚠️ 最高频

**错误信息**：
```
error[E0592]: generic bindings must be unique
```

**触发场景**：同一 `impl` 块中多个泛型函数使用了相同的匿名 lifetime `' '_` 绑定。

**典型代码**（错误示例）：
```rust
impl SomeTrait for MyType {
    fn foo(&self) -> &str { &self.name }
    fn bar(&self) -> &str { &self.value }
    // 两个 &str 返回类型，Rust 推断为同一个 lifetime
    // 编译失败
}
```

**修复方式**：显式标注 lifetime
```rust
impl SomeTrait for MyType {
    fn foo<'a>(&self) -> &'a str { &self.name }
    fn bar<'b>(&self) -> &'b str { &self.value }
}
```

**高发位置**：`crates/cache/src/layered_cache.rs` 频繁出现此问题。

### 1.2 E0432 — 模块导入错误 ⚠️ 高频

**错误信息**：
```
error[E0432]: failed to resolve: could not find `xxx` in `crate_name`
```

**触发场景**：
- `mod tests` 放在文件末尾，但文件末尾有多余的 `}`
- 跨 crate 导入时，包名写错（`kias-common` vs `common`）
- 条件编译 feature 未启用

**典型情况 — `mod tests` 末尾多余 `}`**：
```rust
// 文件末尾
fn helper() {}
}  // <-- 这里多余一个 }，导致整个模块被多包一层

#[cfg(test)]
mod tests {
    // tests 无法找到外层定义的类型
}
```

**诊断方法**：
```bash
tail -5 crates/some-crate/src/some_file.rs
# 确保最后一个符号是文件的结束 }，不是 } 后还有 }
```

**修复方式**：始终检查文件末尾，确认 `}` 只有一层属于文件本身。

---

### 1.3 E0670 — `async fn` in Rust 2015 Edition

**错误信息**：
```
error[E0670]: `async fn` is not permitted in Rust 2015
```

**触发场景**：项目使用 `edition = "2015"` 但代码中有 `async fn`。

**修复方式**：
1. 首选：将 `edition` 升级到 `2021`（workspace 根目录 `Cargo.toml`）
2. 次选：在函数前加 `#[allow(async_fn_in_trait)]`（不推荐）

**当前项目**：已确认使用 `edition = "2021"`，理论上不会有此问题，但旧代码可能有残留。

---

### 1.4 `dead_code` clippy 警告 → 编译失败

**触发场景**：CI 使用 `cargo clippy -- -D warnings`，未使用的代码会导致编译失败。

**高发文件**：
| 文件 | 未使用项 |
|------|---------|
| `patch.rs` | `auto_reboot`、`exclude_packages` |
| `executor.rs` | `get_session`、`cleanup_sessions`、`max_sessions` |
| `config_mgmt.rs` | `baseline_path` |
| `unified_namespace.rs` | `default_read`、`default_write` |

**修复方式**：在未使用的项上加 `#[allow(dead_code)]`

---

### 1.5 fmt-check 失败

**触发场景**：`cargo fmt --check` 在 CI 中失败。

**高发问题**：
- `async fn` 返回类型缩进错误（差4空格）
- JSON 字符串需换行对齐
- `doc_lazy_continuation` 格式问题

**修复方式**：
```bash
cargo fmt
git diff --check
```

---

### 1.6 panic / unwrap() in 生产代码 🚫 零容忍

**铁律**：生产代码中 `unwrap()` / `expect()` / `panic!` 全部清零（2026-05-21 确认全 crate = 0）。

**允许的唯一例外**：在 `#[cfg(test)]` 中，或有明确的 `# SAFETY` 注释。

**检查命令**：
```bash
grep -rn "\.unwrap()" crates/*/src/*.rs | grep -v "test\|#\[cfg"
```

---

### 1.7 bash heredoc 追加代码到现有文件 → struct 重复

**错误方式**：
```bash
cat >> crates/xxx/src/lib.rs << 'EOF'
pub struct Duplicate { ... }
EOF
# 每次运行都追加一份，导致 E0592
```

**正确方式**：写独立文件，用 `sed` 注册到 `lib.rs`
```bash
# 创建新模块
write_file("crates/xxx/src/new_module.rs", "...")
# 注册
sed -i '/mod new_module;/d' crates/xxx/src/lib.rs
sed -i '/^}$/i\    mod new_module;' crates/xxx/src/lib.rs
```

## 二、Cronjob 陷阱

### 2.1 `repeat: "once"` 永远不触发 🚫 最高优先级

**错误配置**：
```json
{
  "schedule": "0 9 * * *",
  "repeat": "once"
}
```

**问题**：`repeat: "once"` 不会在指定时间触发执行！

**正确配置**：
```json
{
  "schedule": "every 60m",
  "repeat": "forever"
}
```
或
```json
{
  "schedule": "0 9 * * *",
  "repeat": "forever"
}
```

**另一陷阱**：`cronjob run` 只是重设 `next_run_at`，不会立即执行任务。

---

### 2.2 TMUX session 断开 → 守护进程中断

**问题**：guardian.sh 守护进程在 TMUX session 断开后停止运行。

**解决方案**：守护进程必须以内嵌方式在 TMUX 内运行，或使用 `nohup`。

## 三、API Key 管理陷阱

### 3.1 key 轮换必须30秒内完成

**问题**：多个 MiniMax API key 轮流使用时，30秒内必须完成 key 更新，否则旧 key 可能被覆盖导致调用失败。

**解决方案**：实现 key 轮换逻辑，确保每次切换在30秒窗口内完成。

### 3.2 tp-s- vs sk-cp- 混淆

**MiniMax API key**：`sk-cp-` 开头 → 正确
**其他服务 key**：`tp-s-` 开头 → 对 MiniMax API 返回 401

**教训**：不同 key 类型混用导致大量 401 错误排查。

## 四、MiniMax/mimo 集成陷阱

### 4.1 长 prompt 必须用文件传参

**问题**：长 prompt 直接传参可能超出 token 限制。

**正确方式**：
```bash
curl -X POST "https://api.minimaxi.com/v1" \
  -d @long_prompt.json  # 传JSON文件
```

### 4.2 M2.7 模型特性

- 响应中有 `reasoning_content` 字段（推理过程）
- `max_tokens` 建议设 6000+
- 按请求计费，每请求最大化 token

### 4.3 mimo 配置路径

**问题**：mimo 是 MiniMax LLM 脚本配置，实际路径在用户本地，未同步到 workspace。

**解决方案**：询问用户 mimo 配置脚本的实际路径后再集成。

## 五、架构/开发陷阱

### 5.1 死代码 = 欺骗 🚫 零容忍

**定义**：写了但没有任何地方调用的代码。

**检查方式**：
```bash
cargo clippy --workspace 2>&1 | grep dead_code
```

**原则**：没有调用方的代码 = 不写。先定义"谁调用它"再写代码。

### 5.2 骨架代码 = 没用 🚫 零容忍

**教训**：骨架代码不被用户接受。必须：
1. 调研竞品实现
2. 下载参考源码到 `/mnt/reference-projects`
3. 基于真实实现编写
4. 先接入再扩展

### 5.3 auto-formatter 修改 AsyncFn 返回类型

**问题**：`crates/cache/src/layered_cache.rs` 中，Rustfmt 反复修改 `AsyncFn` 返回类型的格式，导致格式检查循环。

**解决方案**：最终提交使用 `git checkout` 恢复干净版本。

## 六、Git 操作陷阱

### 6.1 unrelated histories merge

**问题**：本地 main 和远程 main 存在 unrelated histories（历史不相关）。

**解决方案**：
```bash
git pull --allow-unrelated-histories
```
或 force push（谨慎使用）：
```bash
git push --force-with-lease
```

### 6.2 敏感文件意外提交

**问题**：`.env` / `.env.local` 包含真实 API key。

**教训**：确保 `.gitignore` 覆盖所有敏感文件：
```
.env*
.env.local
```

## 七、测试陷阱

### 7.1 测试覆盖率密度极低

**问题**：`im-integration` crate：2738 LOC / 115测试（2.2%密度），`it-change-management/web.rs`：351行仅1个pub函数。

**建议**：任何新功能必须有对应测试，测试覆盖率不低于 50%。

## 九、每次开发前自检清单

```bash
# 1. 确认不会触发 E0592/E0432
cargo check -p <crate-name>

# 2. 确认没有 panic/unwrap
grep -rn "\.unwrap()" crates/*/src/*.rs | grep -v test

# 3. 确认格式正确
cargo fmt --check

# 4. 确认没有 dead_code
cargo clippy --workspace -- -D warnings 2>&1 | grep -E "error|warning"

# 5. 确认 api_keys.json 是 PLACEHOLDER
grep "sk-cp-\|tp-s-" kias/.task-queue/api_keys.json
# 应该只有 PLACEHOLDER

# 6. 确认 cronjob 配置正确
# repeat 字段永远不用 "once"
```
